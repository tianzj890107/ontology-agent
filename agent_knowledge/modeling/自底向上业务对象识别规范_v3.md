# 自底向上业务对象识别与逻辑实体聚合规范 V3

## 1. 目标与层次

输入为物理表、字段、主外键、数据量及可选业务流程信息。输出必须同时覆盖：

1. 完整逻辑实体清单；
2. 业务对象清单；
3. 业务对象与逻辑实体归属关系；
4. 非业务对象及不纳入逻辑模型的表；
5. 信息不足的待确认事项。

必须遵循以下层次，不得倒置：

物理表 → 逻辑实体 → 实体关系图 → 关系边分类 → 候选实体族 → 候选主逻辑实体 → R1–R5 校验 → 业务对象 → 拆合校准。

实体关系图可以用于发现候选边界，但“ER 连通岛”不得直接等同于业务对象。只有符合聚合条件的关系边，才能把多个逻辑实体聚合到同一业务对象。

“不是业务对象”不等于“不是逻辑实体”。R1–R5 只用于判断逻辑实体能否升格为业务对象。

## 2. 逻辑实体识别规则

### L1 全量覆盖
除明确的系统技术表、缓存表、临时表和纯报表派生表外，每个输入表必须形成逻辑实体，或与其他表合并形成一个逻辑实体。

### L2 合并
以下物理表合并为同一逻辑实体：
- 与主表同主键的 1:1 扩展表；
- 垂直拆分表；
- 同结构分表；
- 仅用于历史归档且语义不变的表。

### L3 角色分类
每个逻辑实体必须归入下列一种角色：
- 候选主逻辑实体；
- 从属逻辑实体；
- 关系实体；
- 主数据实体；
- 参考数据实体；
- 观测/事件实体；
- 文档内容实体；
- 派生分析实体；
- 系统技术实体。

### L4 待归属保留
无法确认业务对象归属的逻辑实体标记为“待归属”，不得删除。


## 3. 实体关系图与成岛规则

### G1 双图建模
应同时构建两类关系图：

- **ER 关系图**：依据数据库主键、外键、唯一约束、同主键关系和基数建立；
- **语义关系图**：依据字段业务含义、业务编号、命名模式、流程上下游和人工确认证据建立。

逻辑实体为节点，实体关系为边。语义连接只能作为关系发现证据，不得单独决定业务对象归属。

### G2 关系证据等级
每条实体关系必须记录证据等级：

1. **E1 物理约束证据**：数据库已声明 PK、FK、UNIQUE；
2. **E2 结构匹配证据**：同主键、主键包含父键、业务编号与引用字段稳定匹配；
3. **E3 语义匹配证据**：字段名、字段定义、表名及数据值表明存在关系；
4. **E4 流程或业务确认**：业务流程、单据链、Owner 或领域专家确认。

E3 关系不得在缺少结构或业务确认的情况下直接用于强制聚合，应标记为“逻辑关系待确认”。

### G3 关系边分类
每条边必须归入以下一种关系类型：

| 关系类型 | 定义 | 是否用于同一业务对象聚合 |
| --- | --- | --- |
| 从属依赖边 | 子实体脱离父实体无独立业务意义，身份通常依赖父键 | 是 |
| 同对象扩展边 | 同主键 1:1、垂直拆分、分表、归档或补充属性 | 是 |
| 关系实体边 | 中间实体表达两个或多个独立对象之间的关系 | 否；关系实体单独保留 |
| 跨对象引用边 | 一个独立对象引用另一个独立对象 | 否 |
| 流程衔接边 | 不同生命周期对象之间的来源、转化或履约关系 | 否 |
| 公共主数据引用边 | 组织、人员、客户、供应商、物料等被多对象共享引用 | 否 |
| 派生来源边 | 报表、汇总、宽表或快照来源于业务实体 | 否 |
| 待确认边 | 仅有弱语义证据，关系性质无法确定 | 否 |

### G4 业务对象成岛规则
业务对象实体族只能沿以下边递归聚合：

- 从属依赖边；
- 同对象扩展边。

不得沿以下边合并业务对象：

- 跨对象引用边；
- 流程衔接边；
- 公共主数据引用边；
- 关系实体边；
- 派生来源边；
- 待确认边。

因此，“关系图中的连通分量”不等于“业务对象实体族”。业务对象实体族是仅保留可聚合边之后形成的受限连通子图。

### G5 从属依赖判定
满足以下特征越多，越支持从属依赖边：

- 子表主键包含父表外键；
- 子表使用“父键 + 行号/序号”作为身份；
- 子表无独立业务编号；
- 子表必须随父表创建、删除、关闭或归档；
- 子表记录的是行、明细、附件、审批意见、解析行等；
- 脱离父表后不能被独立管理或复用。

仅存在普通外键，不足以证明从属关系。

### G6 跨对象引用判定
满足以下任一情况，原则上应认定为跨对象引用，而非同对象聚合：

- 被引用实体具有自己的稳定标识和生命周期；
- 被引用实体可被多个业务对象共享；
- 被引用实体可独立创建、维护、查询和确权；
- 删除引用方不会导致被引用实体失去业务意义；
- 关系表现为“订单引用客户”“订单行引用物料”“人员归属部门”等。

### G7 公共节点防巨岛规则
组织、人员、部门、客户、供应商、物料、会计科目、期间等公共实体通常会连接多个业务域。它们的引用边不得参与成岛，否则可能把整个 ERP 图合并为一个巨型业务对象。

公共节点应作为独立业务对象、候选业务对象或参考逻辑实体存在，并通过对象间关系连接其他对象。

### G8 关系实体处理
多对多中间表、分配表、参与者表和映射表应先判断其是否具有独立业务语义：

- 若仅表达两个对象之间的关系，则作为关系实体，不独立升格为业务对象；
- 若具有独立业务编号、状态、生命周期和业务行为，则可转为候选主逻辑实体，再执行 R1–R5；
- 关系实体不得因同时连接多个对象而把这些对象合并。

### G9 生命周期边界优先
即使两个实体存在强 ER 或语义关系，只要它们具有独立标识、独立生命周期和独立管理流程，就必须拆分为不同业务对象。

典型情形包括：

- 采购需求与采购订单；
- 销售订单与发货单；
- 应聘者与员工；
- 生产工单与质量检验单；
- 应收单与收款单。

来源单号、转化单号和上下游外键只表示流程衔接，不表示同一业务对象。

### G10 无关系孤立实体
逻辑实体即使在 ER 图中是孤立节点，也不能据此排除。只要其具备独立业务语义，仍应作为候选主逻辑实体或其他逻辑实体保留，并单独执行 R1–R5 或分类判定。

## 4. 业务对象判定标准

仅对候选主逻辑实体、主数据实体及具有独立管理价值的事件实体执行 R1–R5。

### R1 业务重要性与确权
- 是企业运作管理不可缺少的人、事、物、地信息；
- 来源于业务表、证、单、书，不是纯 IT 产物；
- 有本领域内责任单位。
- 仅被引用或保存冗余快照的实体，不在引用领域重复识别。

### R2 唯一身份标识
- 有稳定的业务编号、单号或代码；
- 仅有技术 ID 时，标记为“?”并提出企业级标识治理问题，不直接否定其业务概念；
- 父键加行号、序号等依赖性标识不支持独立业务对象。

### R3 相对独立与实体族
- 可独立创建、获取、传输、使用并发挥业务价值；
- 从属行、明细、附件、审批意见归入父对象；
- 1:1 扩展、垂直拆分、归档和分表合并；
- 多对多中间表作为关系实体。

### R4 生命周期与状态
满足以下任一证据即可支持：
- 状态、阶段或状态流水；
- 生效/失效日期；
- 启用/停用、关闭、作废标志；
- 版本、轮次；
- 可由业务流程证明的创建、变更、终止过程。
完全缺少证据时标记为“?”，不得仅因字段未出现就断言不存在生命周期。

### R5 可实例化
- 实例数量不能预先穷举，随业务持续增长；
- 存在创建、提交、审批、退回、取消、关闭、维护或操作记录等行为证据之一；
- 固定有限枚举、标签和码值不满足。

## 5. 三值判定

R1–R5 使用三值：
- ✔：有具体表字段、枚举或流程证据；
- ✘：有证据明确不满足；
- ?：输入信息不足。

只有 R1–R5 全部为 ✔ 才列为“已确认业务对象”。
存在“?”且无“✘”时列为“候选业务对象”。
存在任一“✘”时不得列为业务对象，但仍可保留为逻辑实体。

## 6. 非业务对象分类

- 从属逻辑实体：依赖父对象的行、明细、附件、审批意见；
- 关系实体：连接两个或多个实体，本身缺少独立生命周期；
- 参考数据实体：枚举、分类、标签、码表，值域有限；
- 观测/事件实体：采集、量测、流水，记录后通常不流转；
- 派生分析实体：汇总、统计、宽表、报表、集市；
- 文档内容实体：文档及其解析内容，可纳入逻辑模型但通常不是企业核心业务对象；
- 系统技术实体：配置、权限、任务、缓存、技术映射；
- 待确认实体：业务语义或关系证据不足。

## 7. 标准执行步骤

1. 盘点：读取全部表、字段、主键、外键、唯一约束、行数和枚举值。
2. 初筛：标记系统技术表和纯报表派生表，但不得直接删除其他业务表。
3. 逻辑实体化：逐表形成逻辑实体；按 L2 合并拆分表。
4. 角色初判：为每个逻辑实体标记候选主实体、从属实体、关系实体、主数据、参考数据、事件等角色。
5. 建图：同时构建 ER 关系图和语义关系图，并为每条边记录字段证据与证据等级。
6. 边分类：将关系边判定为从属依赖、同对象扩展、关系实体、跨对象引用、流程衔接、公共主数据引用、派生来源或待确认。
7. 受限成岛：只沿从属依赖边和同对象扩展边形成候选业务对象实体族。
8. 主实体识别：在每个候选实体族中选择具有独立身份和管理价值的主逻辑实体；孤立实体也必须单独评估。
9. R1–R5 校验：仅对候选主逻辑实体逐条引用具体表、字段、枚举和关系证据。
10. 拆合校准：按独立生命周期拆分对象；按同主键扩展、分表和重复语义合并。
11. 对象间关系保留：将引用、流程衔接、公共主数据和关系实体边输出为业务对象间关系，不得丢失。
12. 命名与确权：使用业务语言命名，Owner 无证据时标“待确认”。
13. 完备性校验：验证所有输入表、逻辑实体和关系边均有明确去向。

## 8. 强制完备性校验

必须满足：

输入表/视图总数
= 纳入逻辑实体的物理对象数
+ 明确排除的物理对象数
+ 待确认物理对象数。

每个输入表必须出现在以下至少一处：
- 逻辑实体清单；
- 非业务对象/排除清单；
- 待确认清单。

不得出现无解释遗漏。

## 9. 输出

### 一、业务对象清单
业务对象、定义、唯一标识、主逻辑实体、从属实体、生命周期、行为、Owner、R1–R5、结论和置信度。

### 二、逻辑实体清单
物理表、逻辑实体、角色、归属业务对象、主键、外键、数据量、纳入结论和证据。

### 三、实体关系
源实体、目标实体、关系类型、是否参与对象聚合、关系基数、关联字段、证据等级及判定理由。

关系类型必须使用 G3 的标准分类，不得只填写笼统的“外键关系”。

### 四、非业务对象归类
表名、分类、是否纳入逻辑实体、归属对象和具体规则证据。

### 五、待确认问题
仅列信息不足项，明确缺少的信息及应确认的责任方。


## 10. 关键禁止项

- 禁止把完整 ER 连通分量直接识别为一个业务对象；
- 禁止因为存在外键就把两个实体聚合；
- 禁止沿客户、人员、组织、物料等公共主数据引用边成岛；
- 禁止把上下游单据关系误判为同一对象；
- 禁止把关系实体作为桥梁合并其两端对象；
- 禁止仅凭表名或字段名的语义相似度强制归属；
- 禁止遗漏孤立但具有独立业务语义的逻辑实体；
- 禁止在未记录边类型和证据等级的情况下完成实体聚合。
