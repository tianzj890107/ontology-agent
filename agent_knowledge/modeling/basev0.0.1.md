# 智能建模任务：静态私有知识

## 当前规范优先级

`通用业务对象与逻辑实体识别规范v0.0.1.md` 是所有建模任务唯一的核心判定规范。业务属性识别与归属、逻辑实体识别、关系分类、实体族聚合、候选主实体、R1–R5、UNKNOWN、冲突处理和一致性校验必须严格按 v0.0.1 执行。历史规则、示例和来源专项说明只能补充输入提取、字段映射或模板，不得改变或覆盖 v0.0.1 的结论、枚举和判定流程。

## 分层建模与任务级中间态

建模结果不是必须全部成套导出的平面任务，必须按服务端提供的 `modelingPlan` 执行。计划身份固定为：
`repositoryId + taskCode + modelVersion + inputFingerprint`。不同身份的输入、证据和结果文件禁止混用。

```text
TERM ─────────────────────────────── 独立，可单独执行

候选业务属性 → 逻辑实体 → 正式业务属性 → 实体关系
                                      ↓ 校验通过
                       实体族 → 候选主实体 → R1–R5
                                      ↓
                  CONFIRMED / CANDIDATE / REJECTED 业务对象
                                      ↓ 已完成业务对象
                         RULE        METRIC
```

每个 artifact 都可以在单独请求时独立导出。先把当前输入的资产盘点、候选属性、实体、关系、业务对象、术语、规则、指标候选、证据和校验结果写入任务目录的 `mission-work/modeling_state.json`，再从中导出当前 `parseElements` 选择的正式文件。这个中间态不是正式结果，不上传，不放入 `mission-output`，也不记录隐藏思维链。

- `parseElements` 是唯一的识别范围；`expectedFiles` 只约束具体文件名和上传白名单，不能反向选择建模要素；
- 同一任务请求多个类型时可以复用中间态，但不得创建未选择的正式文件；
- 业务对象、规则和指标的业务判断仍要遵循 v0.0.1 的证据和校验规则，但不因其他类型 CSV 尚未生成而阻止当前独立导出。

## 业务属性字段规则

`business_attributes.csv` 必须严格使用本体元模型模板 v0.0.1 的字段顺序，包含新增的 `数据长度` 和 `数据精度`，布尔字段统一使用 `Y/N`：

`logical_entities.csv` 的 `是否主逻辑实体` 也统一使用 `Y/N`，每个业务对象必须且只能有一个 `Y`。

- `是否物理主键` 仅表示来源物理表主键；没有明确物理主键信息时填 `N`，不能据此判断业务身份。
- `是否逻辑主键` 表示业务上唯一标识实体实例的属性；允许多个属性共同组成复合逻辑主键。
- `是否唯一` 表示业务上的唯一标识；属性能在业务范围内唯一识别实体实例时填 `Y`，否则填 `N`，不得仅凭属性名称猜测。
- 复合业务唯一标识必须保留组成属性和组合关系；模板没有唯一组编号时，不得把复合唯一误写成每个单字段都单独唯一，应在执行审计中说明。
- `是否层级编码` 和 `是否层级名称` 当前全部填 `N`；当前不生成维度、层级或钻取映射结果。
- 当同一逻辑实体存在 `XXX编码`（且为逻辑主键）和 `XXX名称` 两个业务属性时，将 `XXX名称` 的 `是否页面显示` 设置为 `Y`。
- 其他所有业务属性的 `是否页面显示` 设置为 `N`，不得留空或使用其他枚举。
- `XXX编码` 与 `XXX名称` 必须属于同一逻辑实体；仅有编码或仅有名称时，不触发页面显示，全部使用 `N`。

## 元模型 v0.0.1 新增元素规则

### 数据长度与数据精度

- `数据长度`、`数据精度` 只记录输入结构、数据库元数据、接口 Schema 或受控文档中明确给出的值；不得依据样例值长度反推定义长度。
- 字符串和定长类型填写声明长度；整数、日期等没有独立精度概念时 `数据精度` 留空；DECIMAL/NUMERIC 按来源声明填写总长度和小数精度。
- 多来源合并且长度或精度冲突时保留冲突证据并进入待确认，不能任取最大值后假装一致。

### 对象关系

- 对象关系连接业务对象，实体关系连接逻辑实体，两者不得混用。只有源、目标均为已确认或已有稳定业务对象时，才生成正式对象关系。
- 关系证据优先取业务流程、生命周期交接、受控业务文档、对象级引用与治理关系；普通外键只能证明实体关系，不能单独证明对象关系。
- `关系类型` 只能使用组合、聚合、分类、关联、依赖、隶属、等价及模板允许的带“关系”后缀形式；证据不足时进入待确认，不得为了消除孤岛强造关系。
- `关系编码` 沿用编码规范中的 `REL` + 6 位流水码；关联的业务对象编码必须引用已有或本次生成的稳定编码。

### 状态

- 状态必须归属到明确业务对象。来源优先为状态字段及码表、状态机/流转配置、流程节点、代码枚举、事件日志和受控文档。
- 普通类型、分类、布尔标志和处理结果不是生命周期状态；只有能表达业务对象阶段性处境且可由业务操作、时间或事件驱动变化时，才识别为状态。
- `是否终态=Y` 表示正常流转不再继续；`是否主终态=Y` 必须同时满足 `是否终态=Y`。取消、作废等次要终态不能仅因无后续记录自动判为主终态。
- 状态编码优先沿用来源稳定编码。编码规范 v0.0.1 未声明状态新编码格式，无稳定来源时标记待确认，禁止自定义前缀。

### 事件

- 事件是业务执行过程中已发生或可明确触发的关键动作节点，应有动作、消息、流程、审计日志、状态变化或系统同步证据，并能说明触发结果。
- 普通数据行、静态属性、状态值本身不是事件；“状态发生变化”的动作可以是事件，变化后的状态仍应写入状态结果。
- `事件名称` 按元模型含义填写标准英文名称，`事件中文名称` 填业务中文名；没有可靠英文名称时留空并待确认，不得用拼音替代。
- 事件编码优先沿用来源稳定编码。编码规范 v0.0.1 未声明事件新编码格式，无稳定来源时标记待确认，禁止照抄样例的 `E` 前缀。

### 业务规则六列映射

- 正式业务规则按 `规则编码,规则名称,规则描述,触发条件,判断或结果,处置动作` 输出；详细形式化表达、校验 SQL、证据、强度和置信度留在任务中间态与执行审计。
- `触发条件` 对应 WHEN/ON/IF 前置条件，`判断或结果` 对应校验结论或推导结果，`处置动作` 对应 THEN 后续动作；来源只表达约束但没有处置动作时不得臆造，应标记待确认。
- 元模型、模板和样例统一使用“规则编码”；编码使用 `R` + 7 位流水码。

# 通用业务对象与逻辑实体识别规范 v0.0.1

## 1. 适用范围

本规范用于从任意数据源中自底向上识别：物理数据资产、逻辑实体、实体关系、实体族、业务对象、非业务对象及待确认事项。

适用于关系型数据库、数据仓库与数据湖、API Schema、JSON/XML/Avro/Protobuf、文档库、图数据库、事件流、文件型数据源等。

本规范不依赖任何特定行业、产品、系统、表名前缀、字段名、英文后缀或固定业务词典。

## 2. 核心原则

### 2.1 分层原则

必须按照以下顺序执行：

```text
数据源资产 → 物理对象 → 候选业务属性 → 逻辑实体 → 业务属性归属
→ 实体关系 → 关系分类 → 实体族 → 候选主实体 → 业务对象判定 → 业务对象目录
```

禁止跳过逻辑实体层，直接从物理表、文档或接口识别业务对象。

### 2.2 全量覆盖原则

每个输入资产必须进入以下至少一类：已识别逻辑实体、明确排除的技术或派生资产、待确认资产。不得无解释遗漏。

### 2.3 业务对象与逻辑实体分离原则

“不是业务对象”不等于“不是逻辑实体”。从属实体、关系实体、参考实体、观测实体、文档内容实体和派生实体均可作为逻辑实体存在，但通常不独立构成业务对象。

### 2.4 证据优先原则

任何结论必须由可追溯证据支持。证据不足时必须输出 UNKNOWN 或待确认，不得臆造字段、流程、状态、Owner 或生命周期。

### 2.5 强反证优先原则

当正向证据与反向证据冲突时，强反证优先于弱正向证据。例如：独立身份优先于名称相似，独立生命周期优先于外键连接，业务独立管理优先于同系统或同模块。

### 2.6 配置与核心规范分离原则

以下内容不得写死在通用核心规范中：特定行业术语、特定表名和字段名、特定系统前缀、固定英文命名后缀、固定业务对象词典、固定分值和固定权重。这些内容必须通过外部配置加载。

### 2.7 事实证据门禁原则

一致性校验只能发现缺口，不能成为创造事实的证据。校验器是只读语义检查器，返回的缺失关系、结构完整性要求、ERROR/WARNING、重试次数和“校验未通过”均不得直接或间接新增实体、属性、关系、业务对象或规则。

关系必须先进入结构化关系决策，状态只能为 `CONFIRMED`、`CANDIDATE`、`UNRESOLVED` 或 `REJECTED`。正式实体关系结果只允许输出 `CONFIRMED` 且有可追溯证据的关系；`CANDIDATE`、`UNRESOLVED` 和 `REJECTED` 只能保留在候选/审计/待确认中。`LLM_SEMANTIC_INFERENCE`、业务常识、名称相似或单一弱证据不能单独确认关系；关系缺少真实来源时必须保留 `UNKNOWN/UNRESOLVED`，记录缺失证据和待确认问题。

派生实体没有明确来源时，血缘缺口是 `WARNING/NEEDS_CONFIRMATION`，不是要求 Agent 猜测来源。只有新取得独立的外键、声明约束、视图/ETL SQL lineage、代码引用、显式配置或已有本体证据，才允许把候选或未知关系升级为正式事实。结构性修复与语义修复必须分离：CSV 表头、编码和格式可以结构性修复；新增或改变业务语义必须有新证据。

## 3. 输入要求

### 3.1 最低输入

每个数据资产应尽可能提供：资产名称、资产类型、结构定义、字段或属性、数据类型、身份约束、引用关系、数据规模、样例或枚举、来源系统、更新时间。

### 3.2 可选增强输入

可提供：业务定义、数据字典、业务流程、状态机、生命周期、Data Owner、责任组织、数据契约、API 文档、消息定义、领域模型、使用场景、上下游血缘和数据质量规则。

### 3.3 统一输入模型

不同数据源必须通过适配器转换为统一输入模型，至少包含：

```text
Asset
Attribute
IdentityConstraint
Relationship
Cardinality
InstanceEvidence
LifecycleEvidence
GovernanceEvidence
SemanticEvidence
LineageEvidence
```

## 4. 统一证据模型

### 4.1 证据维度

所有实体、关系和业务对象判定均使用以下证据维度：

- 结构证据：主键、唯一约束、外键、嵌套、组成、基数、同主键、复合键、数据分布等。
- 语义证据：名称、定义、字段描述、样例值、枚举、文档上下文、接口说明、业务术语映射。
- 行为证据：创建、变更、提交、审批、关闭、失效、撤销、发布、归档、事件发生、状态转换、版本变化。
- 治理证据：Owner、责任组织、数据契约、权威来源、质量责任、确权记录。
- 血缘与使用证据：来源、派生过程、上下游依赖、消费场景、业务流程位置、复用情况。

### 4.2 证据等级

每条证据使用以下等级：

- STRONG：直接、明确、可验证；
- MODERATE：较强支持，但存在解释空间；
- WEAK：仅提供倾向；
- NONE：没有证据；
- CONTRADICTORY：与目标结论冲突。

不得将多个弱证据机械累加为强证据。

### 4.3 证据来源可靠性

每条证据还应记录来源可靠性：

- AUTHORITATIVE：业务 Owner、正式数据契约、权威主数据；
- CONTROLLED：正式系统结构、受控文档、稳定约束；
- OBSERVED：数据样例、数据分布、运行行为；
- INFERRED：名称、模式、语义推断；
- UNVERIFIED：未经验证。

## 5. 物理对象识别

物理对象是数据源中的实际存储或交换结构，包括表、视图、文件、文档、API 资源、消息事件、图节点、图边、索引、数据集、Topic 和 Schema。

物理对象先分为：业务数据资产、参考数据资产、观测或事件资产、文档资产、派生分析资产、系统技术资产、未分类资产。此阶段不直接识别业务对象。

## 6. 业务属性识别

### 6.1 业务属性定义

业务属性是用于描述、识别、分类、度量或管理逻辑实体实例的最小业务语义单元。

业务属性来源于物理字段、文档元数据、接口参数、消息载荷属性、图属性或其他数据结构，但不得直接等同于物理字段。

一个业务属性可以由：

- 一个物理字段直接映射；
- 多个物理字段组合形成；
- 一个物理字段拆分形成；
- 计算或转换规则形成；
- 外部语义或治理信息补充形成。

### 6.2 业务属性识别顺序

业务属性识别分为两个阶段。

#### 阶段一：候选业务属性识别

在逻辑实体识别前，对全部物理字段进行语义化，形成候选业务属性。

候选业务属性至少记录：

- 来源物理对象；
- 来源字段或属性；
- 原始名称；
- 数据类型；
- 是否可空；
- 主键、唯一约束或引用约束；
- 样例值；
- 枚举值；
- 字段描述；
- 初步业务含义；
- 初步属性角色；
- 证据等级。

#### 阶段二：业务属性正式归属

在逻辑实体初步形成后，将候选业务属性正式归属到逻辑实体，并根据属性归属结果重新检查逻辑实体是否需要合并或拆分。

业务属性不得在未确认逻辑实体归属的情况下直接成为最终业务属性。

### 6.3 业务属性角色

每个业务属性必须指定一个主角色：

- `IDENTIFIER`：标识属性；
- `DESCRIPTIVE`：描述属性；
- `CLASSIFICATION`：分类属性；
- `STATUS`：状态或阶段属性；
- `TEMPORAL`：日期、时间、期间或有效期属性；
- `MEASURE`：数量、金额、比率或度量属性；
- `REFERENCE`：指向其他逻辑实体的引用属性；
- `LOCATION`：位置或空间属性；
- `PARTY`：人员、组织或责任主体属性；
- `DOCUMENT`：文档、附件或内容属性；
- `AUDIT`：创建、修改、审批、版本或操作审计属性；
- `TECHNICAL`：仅服务于存储、同步、分区、缓存或系统运行的技术属性；
- `DERIVED`：通过计算、汇总或转换得到的派生属性；
- `UNCLASSIFIED`：信息不足，暂无法分类。

每个业务属性必须且只能有一个主角色，可附加辅助标签。

### 6.4 业务属性成立条件

物理字段满足以下至少一项时，可识别为候选业务属性：

- 描述业务实例的身份；
- 描述业务实例的状态、特征或分类；
- 描述业务实例的时间、位置或数量；
- 表达与其他业务实体的引用；
- 支持业务行为、流程或治理；
- 在业务定义、数据契约或使用场景中具有明确意义。

仅用于以下目的的字段，默认不识别为业务属性：

- 数据库存储地址；
- 分区键但无业务意义；
- 缓存键；
- 同步游标；
- 消息偏移量；
- 系统运行标志；
- 技术校验值；
- 内部序列号；
- 临时处理状态；
- 纯展示格式字段。

若技术字段同时承担稳定业务身份或治理用途，不得仅因其技术实现形式而排除。

### 6.5 标识属性识别

标识属性用于稳定区分逻辑实体实例。

标识可以是：

- 单一属性；
- 复合属性；
- 自然标识；
- 代理标识；
- 外部标识；
- URI；
- 文档标识；
- 事件标识。

判断标识时应检查：

- 唯一性；
- 稳定性；
- 非空性；
- 是否可被引用；
- 是否依赖其他实体；
- 是否在目标业务范围内有效。

复合标识不得自动视为从属标识，代理标识也不得自动视为无业务意义。

### 6.6 引用属性识别

引用属性表示逻辑实体之间的关系线索。

引用属性只证明“可能存在关系”，不能单独证明：

- 组成关系；
- 扩展关系；
- 同一业务对象；
- 从属关系；
- 生命周期依赖。

引用属性必须在实体关系识别阶段结合身份、基数、生命周期和业务独立性进一步分类。

### 6.7 状态与生命周期属性识别

以下属性可作为生命周期证据：

- 状态；
- 阶段；
- 生效时间；
- 失效时间；
- 创建时间；
- 关闭时间；
- 版本；
- 轮次；
- 发布状态；
- 审批状态；
- 事件发生时间；
- 归档标志。

不存在显式状态属性，不等于逻辑实体没有生命周期。

生命周期还可以通过事件、版本、行为记录、流程文档或治理规则证明。

### 6.8 属性簇与逻辑实体边界

候选业务属性应按以下维度形成属性簇：

- 共同身份；
- 共同生命周期；
- 共同业务含义；
- 共同治理责任；
- 共同创建和维护行为；
- 共同消费和使用场景。

若一个物理对象中的字段形成两个或多个相互独立的属性簇，应考虑拆分为多个逻辑实体。

若多个物理对象中的属性具有相同身份、生命周期和治理责任，应考虑合并为同一逻辑实体。

属性簇只是逻辑实体边界证据，不能单独替代实体独立性判断。

### 6.9 属性标准化

业务属性正式归属逻辑实体后，应进行标准化：

- 使用业务语言命名；
- 给出明确业务定义；
- 统一数据类型语义；
- 统一单位和精度；
- 统一枚举值含义；
- 识别同义属性；
- 识别一词多义；
- 区分原始属性和派生属性；
- 保留物理字段映射；
- 记录转换和计算规则。

标准化不得修改源数据事实，也不得臆造不存在的业务含义。

### 6.10 业务属性输出要求

业务属性清单至少包含：

- 逻辑实体编码；
- 逻辑实体名称；
- 业务属性编码；
- 业务属性名称；
- 标准名称；
- 业务定义；
- 属性角色；
- 数据类型；
- 是否标识属性；
- 是否必填；
- 枚举或值域；
- 单位和精度；
- 来源物理对象；
- 来源字段；
- 转换规则；
- 证据等级；
- 置信度；
- 待确认事项。

### 6.11 业务属性一致性校验

必须执行以下校验：

1. 每个非技术业务字段必须映射到业务属性，或明确说明排除原因；
2. 每个业务属性必须归属一个逻辑实体；
3. 每个标识属性必须有唯一性或稳定性证据；
4. 每个引用属性必须对应实体关系或待确认关系；
5. 每个状态属性必须明确值域或状态语义，无法确认时进入待确认；
6. 每个派生属性必须记录来源和计算规则；
7. 每个技术属性必须说明其技术用途；
8. 同一逻辑实体内不得存在语义重复但未合并的业务属性；
9. 同名异义属性必须分别定义；
10. 属性归属变化后必须重新校验逻辑实体边界。

## 7. 逻辑实体识别

### 7.1 定义

逻辑实体是对一组具有相同业务语义、身份和属性结构的数据实例的抽象。

一个物理对象可映射为一个或多个逻辑实体，也可能只是某逻辑实体的一部分；多个物理对象也可合并为一个逻辑实体。

### 7.2 生成条件

满足以下至少一项，可形成逻辑实体：

- 表示可区分的一类实例；
- 具有稳定属性集合；
- 具有可识别身份；
- 在业务、数据或流程中被单独引用；
- 在数据契约或接口中作为独立资源；
- 在文档或事件中形成稳定语义单元。

### 7.3 合并条件

多个物理对象仅在以下条件均满足时才可合并：

- 表达同一业务概念；
- 身份一致；
- 生命周期一致；
- 治理责任一致；
- 不存在独立管理边界；
- 差异仅来自物理拆分、分区、存储层级或技术实现。

### 7.4 拆分条件

一个物理对象出现以下情况时应拆分为多个逻辑实体：

- 包含多个独立身份体系；
- 包含多个独立生命周期；
- 混合多个可独立管理概念；
- 存在重复组或嵌套对象；
- 不同字段组具有不同 Owner；
- 不同字段组可独立创建、修改或消费。

### 7.5 逻辑实体角色

只使用以下主角色：

- CANDIDATE_MAIN_ENTITY
- DEPENDENT_ENTITY
- RELATIONSHIP_ENTITY
- MASTER_DATA_ENTITY
- REFERENCE_DATA_ENTITY
- OBSERVATION_EVENT_ENTITY
- DOCUMENT_CONTENT_ENTITY
- DERIVED_ANALYTICAL_ENTITY
- SYSTEM_TECHNICAL_ENTITY
- UNCLASSIFIED_ENTITY

每个实体必须且只能有一个主角色，可附加辅助标签。

## 8. 实体关系识别

### 8.1 通用关系类型

- COMPOSITION：组成关系。子实体身份或生命周期依赖父实体，可参与聚合。
- EXTENSION：同一概念的属性扩展。身份、生命周期和治理责任一致，可参与聚合。
- ASSOCIATION：两个独立实体之间的业务关联，不参与聚合。
- REFERENCE：一个实体引用另一个实体的身份或属性，不参与聚合。
- TRANSFORMATION：来源、转换、履约、结算或派生关系，不参与聚合。
- OBSERVATION_OF：事件、日志、测量或观测针对某对象，不参与聚合。
- SPECIALIZATION：泛化/特化关系，默认不作为组成关系处理。
- UNKNOWN：证据不足，不参与聚合。

COMPOSITION 的全局方向契约固定为：`source = component/dependent/child`，`target = owner/parent`。不能因为实体出现在 COMPOSITION 任意一端就判定合法；必须同时验证方向、source/target role capability、owner 唯一性、循环和证据状态。REFERENCE、ASSOCIATION、TRANSFORMATION、OBSERVATION_OF、SPECIALIZATION 不得参与业务对象聚合。

### 8.2 关系输出要求

每条关系必须记录：源实体、目标实体、关系类型、基数、关联属性、结构证据、语义证据、行为证据、是否参与聚合、置信度和冲突证据。

### 8.3 聚合限制

只有 COMPOSITION 和 EXTENSION 可以参与业务对象实体族聚合。

## 9. 关系判定决策树

按以下顺序执行：

1. 两端是否表达同一身份、同一生命周期、同一治理责任？是则优先判断 EXTENSION。
2. 一端是否依赖另一端身份，且无法独立管理？是则优先判断 COMPOSITION。
3. 两端是否均可独立存在，关系本身是否表达业务关联？是则判断 ASSOCIATION。
4. 一端是否仅保存另一端身份或属性引用？是则判断 REFERENCE。
5. 一端是否由另一端转换、产生、履约或派生？是则判断 TRANSFORMATION。
6. 一端是否记录对另一端的事件、测量、日志或状态观测？是则判断 OBSERVATION_OF。
7. 是否存在明确父类—子类语义？是则判断 SPECIALIZATION。
8. 证据不足则 UNKNOWN。

名称相似、同系统、同模块、同前缀或普通外键均不足以单独确定关系类型。

## 10. 业务对象识别

### 10.1 定义

业务对象是组织在业务运行中需要独立识别、管理、使用、治理和追踪的一类实例集合，可对应人、组织、事、物、地、权利、义务、规则、文档、事件、资源、合约或业务状态载体。

### 10.2 候选主实体

以下逻辑实体可进入业务对象候选：

- CANDIDATE_MAIN_ENTITY；
- MASTER_DATA_ENTITY；
- 具有独立管理价值的 OBSERVATION_EVENT_ENTITY；
- 具有独立治理价值的 DOCUMENT_CONTENT_ENTITY；
- 具有独立身份和生命周期的 RELATIONSHIP_ENTITY。

### 10.3 实体族形成

1. 以逻辑实体为节点；
2. 只保留 COMPOSITION 和 EXTENSION；
3. 只对已确认且通过 COMPOSITION/EXTENSION 语义校验的边求连通分量；
4. 每个连通分量形成候选实体族；
5. 每个实体族必须有且只能有一个候选主实体；
6. 无主实体、多主实体、Owner 冲突、方向错误或 COMPOSITION 循环的实体族不得进入正式业务对象。

完整 ER 连通图不得直接作为业务对象实体族。

## 11. 业务对象判定标准

### R1 业务意义与治理责任

判断是否表示目标业务范围内的重要概念，是否有明确业务用途、治理主体、责任域或权威来源，且不是纯技术实现产物。

- 直接业务和治理证据充分：PASS
- 明确仅为技术或冗余产物：FAIL
- 证据不足：UNKNOWN

### R2 稳定身份

判断实例是否可以稳定区分，身份是否在目标业务范围内稳定，是否可用于引用、交换和追踪。

允许单字段键、复合业务键、自然键、代理键、外部标识、URI、文档标识和事件标识。不得因使用复合键或代理键直接否决。

- 身份稳定且可追踪：PASS
- 明确不存在独立身份：FAIL
- 无法确认：UNKNOWN

### R3 独立性

判断是否可被独立理解、创建、管理、查询、传输或消费，脱离其他对象后是否仍有业务意义，是否具有独立治理边界。

- 独立性明确：PASS
- 明确依赖父对象：FAIL
- 证据不足：UNKNOWN

### R4 生命周期

判断是否存在产生、变化、失效、终止或永久留存机制，是否存在状态、版本、生失效日期、事件发生时间或流程阶段。

不得强制要求必须存在状态字段；不可变事件也可以具有“发生并留存”的生命周期。

- 生命周期明确：PASS
- 明确无生命周期，仅为静态有限值或纯派生结果：FAIL
- 无法确认：UNKNOWN

### R5 可实例化

判断是否可以产生多个可区分实例，实例是否由业务、操作、事件或治理活动产生，是否可被创建、记录、引用或维护。

- 可形成业务实例集合：PASS
- 仅为固定值域、纯技术配置或纯计算结果：FAIL
- 信息不足：UNKNOWN

## 12. 业务对象结论

- R1–R5 全部 PASS：CONFIRMED
- 无 FAIL 且至少一个 UNKNOWN：CANDIDATE
- 任一规则为 FAIL：REJECTED

置信度不得改变结论，只描述证据可靠性。

正式业务对象目录只收录 CONFIRMED；候选业务对象单独管理 CANDIDATE；驳回候选单独记录 REJECTED。

### 12.1 业务对象决策证据链

每一个实际参与判定的业务对象候选都必须保留结构化决策记录，写入任务内部 `modeling_state.json` 的 `businessObjectDecisions`，并稳定导出到 `mission-work/business_object_decisions.csv`。记录必须分别保存 R1、R2、R3、R4、R5 的 `PASS`、`FAIL` 或 `UNKNOWN`、对应证据和来源引用、冲突、未知原因、确认问题、建议确认角色与置信度。没有证据不能为了填充字段而生成解释；没有反证不能把证据缺失判为 FAIL。

最终决策必须由代码按 R1–R5 重算：任一 FAIL 为 REJECTED；无 FAIL 且至少一个 UNKNOWN 为 CANDIDATE；全部 PASS 才为 CONFIRMED。置信度不改变决策。CONFIRMED 才能进入正式 `business_objects.csv`；CANDIDATE 和 REJECTED 只进入决策审计，不得丢弃，也不能因此删除对应逻辑实体。正式输出与决策审计必须通过编码一致性校验。

## 13. 命名规范

### 13.1 命名与识别分离

源名称只作为语义证据，不直接决定业务对象边界。标准名称是治理产出，不是识别前提。

### 13.2 通用命名要求

标准名称必须：表达业务概念、与定义一致、在目标本体范围内唯一、不包含无业务意义的物理实现信息、不依赖具体数据库前缀、不直接复制不透明缩写，并遵循目标组织的语言和命名策略。

### 13.3 命名策略配置

以下内容必须由项目配置提供：中文命名规则、英文命名规则、大小写规则、单复数规则、缩写词典、禁用词、同义词词典、领域术语词典和技术前缀词典。

通用规范不得规定具体英文后缀。

### 13.4 名称证据可靠性

先评估数据源命名质量，包括命名一致性、缩写透明度、定义覆盖率、名称与结构一致性、名称与样例值一致性。

命名质量高时，名称可作为 MODERATE 语义证据；命名质量低时，只能作为 WEAK 证据。名称不得单独形成 COMPOSITION、EXTENSION 或业务对象结论。

## 14. 冲突处理

### 14.1 默认优先级

1. 权威业务确认和数据契约；
2. 独立身份与生命周期证据；
3. 结构约束和基数；
4. 运行数据和行为证据；
5. 业务定义与字段语义；
6. 名称和命名模式。

### 14.2 冲突输出

出现冲突时必须记录：支持证据、反对证据、采用的优先级、当前结论、待确认问题和需确认责任方。不得静默忽略冲突。

## 15. 数据源适配器规范

### 15.1 关系型数据库适配器

提取表、视图、字段、PK、FK、UNIQUE、基数、行数、枚举、数据分布和血缘。不得将普通外键自动解释为组成关系。

### 15.2 文档库适配器

提取文档、章节、元数据、引用、类型、版本、发布和归档信息。不得将章节自动识别为业务对象。

### 15.3 事件流适配器

提取事件类型、事件标识、发生时间、聚合标识、载荷、因果关系、版本、生产者和消费者。事件没有状态字段时，仍可具有明确生命周期。

### 15.4 API 适配器

提取资源、路径、请求响应 Schema、资源标识、嵌套关系、CRUD 操作、版本和错误语义。API 嵌套不得自动解释为组成关系。

### 15.5 图数据库适配器

提取节点类型、边类型、属性、唯一约束、方向、基数和子图模式。图连通分量不得直接解释为业务对象。

### 15.6 数据仓库适配器

区分业务源实体、维度、事实、快照、聚合、派生指标和数据集市。事实表与维度表的物理建模角色不得直接等同于业务对象角色。

### 15.1 业务规则类型化验证

业务规则必须先分类再验证。完整性约束使用 violation 语义；告警/检测规则使用 hit 或 match 语义，条件命中不是 violation，命中率不能自动否定规则；计算规则比较 expected 与 actual；状态流转需要历史；资格/决策规则需要 outcome 或 action。无法可靠分类时保留 UNKNOWN/NEEDS_CLASSIFICATION，不能默认按完整性约束验证。规则类型与 enforcement 独立，样本中 0 violation 只能说明观察到一致性，不能证明 ENFORCED。

## 16. 领域与项目配置接口

通用协议允许加载：

```text
DataSourceProfile
DomainVocabulary
NamingPolicy
GovernancePolicy
IdentityPolicy
LifecyclePolicy
RelationshipPolicy
ExclusionPolicy
ConfidencePolicy
```

项目配置只能增加领域术语、同义词、识别线索、证据来源、命名策略和治理责任。

项目配置不得绕过 R1–R5，不得将弱命名证据提升为决定性证据，不得允许非组成关系参与聚合，不得隐藏 UNKNOWN 或冲突，不得取消覆盖校验。

## 17. 输出要求

### 17.1 正式业务对象清单

至少包含：业务对象编码、名称、定义、主逻辑实体、从属实体、身份、生命周期、行为、Owner、R1–R5、结论、置信度和证据摘要。

### 17.2 候选业务对象清单

至少包含：候选名称、主逻辑实体、UNKNOWN 规则、缺失证据、待确认事项和需确认责任方。

### 17.3 驳回候选清单

至少包含：候选名称、失败规则、最终逻辑实体角色、驳回证据和是否保留为逻辑实体。

### 17.4 逻辑实体清单

至少包含：逻辑实体编码、名称、定义、角色、物理来源、身份、属性、归属实体族、归属业务对象、证据和置信度。

### 17.5 业务属性清单

至少包含：逻辑实体编码、业务属性编码、名称、标准名称、业务定义、属性角色、数据类型、标识属性标记、必填标记、值域、单位和精度、物理来源、转换规则、证据、置信度和待确认事项。

### 17.6 实体关系清单

至少包含：源实体、目标实体、关系类型、基数、关联属性、是否参与聚合、证据等级、置信度、判定理由和冲突说明。

### 17.7 非业务对象清单

至少包含：资产或实体、分类、是否进入逻辑模型、不构成业务对象的原因和证据。

### 17.8 待确认问题

仅列信息不足项，必须包含：待确认主题、缺失信息、影响结论、需确认角色或责任方、建议确认方式。

## 18. 自动一致性校验

1. 覆盖校验：输入资产总数 = 已映射资产数 + 明确排除数 + 待确认数。
2. 业务属性覆盖校验：每个非技术业务字段必须映射为业务属性，或明确说明排除原因。
3. 业务属性归属校验：每个业务属性必须归属一个逻辑实体；标识、引用、状态和派生属性须分别满足 v0.0.1 的证据与追溯要求。
4. 唯一角色校验：每个逻辑实体和业务属性必须且只能有一个主角色。
5. 从属实体校验：每个 DEPENDENT_ENTITY 必须至少有一条 COMPOSITION 边。
6. 关系实体校验：每个 RELATIONSHIP_ENTITY 必须至少连接两个独立实体，且不得桥接聚合两端对象。
7. 聚合边校验：参与聚合的边只允许 COMPOSITION 和 EXTENSION。
8. 主实体校验：每个业务对象必须且只能有一个主逻辑实体。
9. 多主实体冲突校验：不得自动选择，必须进入待确认。
10. R1–R5 结论一致性校验。
11. UNKNOWN 闭环校验：每个 UNKNOWN 必须对应待确认问题。
12. 证据完整性校验：每个实体角色、属性角色、关系类型和规则判定必须有具体证据来源。
13. 命名校验：标准名称必须符合项目 NamingPolicy。
14. 冲突校验：存在 CONTRADICTORY 证据时，必须记录处理结果。
15. 血缘校验：派生分析实体必须至少有一个已确认来源关系；没有足够证据时输出 `MISSING_DERIVATION_LINEAGE` WARNING 和待确认问题，不得自动补造来源。
16. 审计校验：每个最终结论必须可追溯到输入、证据、规则、冲突处理和输出结论。

## 19. 标准执行流程

Agent 必须依次执行：

1. 加载通用核心规范；
2. 加载数据源适配器；
3. 加载项目配置；
4. 盘点全部输入资产；
5. 提取结构、字段和数据样例；
6. 建立统一输入模型；
7. 识别候选业务属性并分类属性角色；
8. 根据身份、生命周期、治理责任和属性簇识别逻辑实体；
9. 将业务属性正式归属逻辑实体；
10. 根据属性归属结果重新校验实体拆分与合并；
11. 识别并分类实体关系；
12. 只沿 COMPOSITION 和 EXTENSION 构建实体族；
13. 确定候选主实体；
14. 执行 R1–R5；
15. 生成正式、候选和驳回目录；
16. 生成非业务对象分类；
17. 生成待确认问题；
18. 执行自动一致性校验；
19. 结构性错误不得输出正式结果；语义证据不足可以输出诚实的不完整结果和 WARNING，但不得输出无证据的正式关系；
20. 输出审计记录。

## 20. 禁止事项

- 禁止把物理表等同于逻辑实体；
- 禁止把逻辑实体等同于业务对象；
- 禁止根据 ER 连通分量直接成岛；
- 禁止根据普通外键直接聚合；
- 禁止根据同模块、同前缀或同系统聚合；
- 禁止根据英文后缀直接决定角色；
- 禁止将名称相似视为同一概念；
- 禁止将复合键直接判为从属；
- 禁止强制要求所有业务对象必须有状态字段；
- 禁止将不可变事件排除在生命周期之外；
- 禁止把有限集合自动认定为技术数据；
- 禁止忽略孤立实体；
- 禁止隐藏 UNKNOWN；
- 禁止将低置信度直接改为 FAIL；
- 禁止用项目配置绕过核心规则；
- 禁止输出无证据结论。

## 21. 通用协议与项目 Profile 的边界

通用协议负责：概念模型、证据模型、判定框架、关系分类、R1–R5、输出结构和一致性校验。

项目 Profile 负责：数据源结构映射、领域术语、同义词、命名规则、Owner 映射、已知生命周期、已知身份规则和已知排除项。

通用协议必须独立于任何具体 Profile 正常运行。Profile 缺失时，Agent 应输出更多 UNKNOWN，而不是自行补充领域知识。

### 21.1 校验缺口与正式事实的边界

本规范或数据模型参考中出现“补充缺失关系”“消除孤岛”“满足每个角色必须存在某关系”等表述时，其含义是：继续查找独立证据，或把缺口记录为 CANDIDATE、UNRESOLVED 和待确认问题；不能据此直接创建正式关系。Evidence Gate 的优先级高于结构完整性要求。校验器是只读检查器，不是事实来源；校验发现缺失关系只能生成 WARNING/NEEDS_CONFIRMATION，不能生成关系、选择 Owner、选择主逻辑实体或改变关系类型。只有新的、可追溯的独立证据才允许把候选或未知结论升级为 CONFIRMED 并进入正式 CSV。

## Evidence Gate 最终优先级（覆盖参考表述）

公共规则、模板或历史参考中关于“避免孤岛”“补充缺失关系”“每个角色必须存在某关系”的描述，只能驱动证据检索、候选记录和待确认问题，不能直接创建正式事实。孤岛、缺失血缘、缺少 Owner、多主或无主都可以作为 WARNING/NEEDS_CONFIRMATION 保留。校验器是只读检查器，校验结果、完整性要求和重试次数都不构成证据；只有新的、可追溯的独立证据经过 Evidence Gate 后，才能把 CANDIDATE/UNRESOLVED 升级为 CONFIRMED 并进入正式 CSV。

## Business Object 决策审计最终优先级

每一个实际评估的 Business Object candidate 都必须保留 R1、R2、R3、R4、R5 的 PASS/FAIL/UNKNOWN、逐项证据与 provenance，并写入 `mission-work/business_object_decisions.csv`。任一 FAIL → REJECTED；无 FAIL 且有 UNKNOWN → CANDIDATE；全部 PASS → CONFIRMED。confidence 不能改变这个 deterministic decision，且必须在建模时直接输出 0–100 的数值，不得使用 HIGH/MODERATE/LOW 标签或由导出器猜测数值。没有反证不能判 FAIL，没有真实证据不能伪造 PASS；CANDIDATE、REJECTED 不得丢弃，只有 CONFIRMED 才能进入正式 `business_objects.csv`，被 REJECTED 的候选对应逻辑实体仍须保留。

## Business Rule 类型化验证最终优先级

业务规则必须先按语义类型选择验证策略：完整性约束使用 violation 统计；告警/检测规则使用 hit/match 统计，条件命中不是 violation，命中率不能自动驳回；计算规则比较 expected 与 actual；状态流转需要历史；资格/决策规则需要 outcome/action。无法可靠分类时保留 UNKNOWN/NEEDS_CLASSIFICATION，不能默认按完整性约束验证。规则类型与 enforcement 分离，样本中 0 violation 不能证明 ENFORCED。规则决策与存在、验证、强制状态互相独立：CONFIRMED 只需要规则存在证据（声明、实现、OBSERVED_PATTERN 数据模式或验证证据），即可进入正式规则目录；OBSERVED_PATTERN + CONFIRMED + 强制状态=UNKNOWN/NOT_ENFORCED 是合法正式规则，缺强制证据只降低强制状态、缺验证证据只降低验证状态，只有连存在证据都没有时才降为 CANDIDATE，不得把强制状态标成 ENFORCED。

## Decision Audit 与不确定性最终优先级

Schema 必填字段、CSV 模板完整性、Validator ERROR/WARNING、孤岛检查和结果完整性都不是业务事实证据；不能为了填空、补齐关系或满足模板创造 Owner、生命周期、member-of、lineage、处置动作或业务对象归属。逻辑实体允许 `ASSIGNED`、`UNASSIGNED`、`UNRESOLVED`；后两者必须保存原因和缺失证据，不得硬填正式 Business Object。

所有语义判定必须先进入结构化 Decision Layer，再由确定性 Validator 和 Generator 消费。每个候选、关系、规则、指标和逻辑实体的 CONFIRMED、CANDIDATE、UNRESOLVED、REJECTED/UNKNOWN 都必须落盘到当前任务 `mission-work/` 的五个固定决策审计 CSV：`business_object_decisions.csv`、`relation_decisions.csv`、`rule_decisions.csv`、`indicator_decisions.csv`、`logical_entity_decisions.csv`，以及 `validation_report.json` 与 `modeling_state.json`。五个 CSV 强制使用决策审计模板 `v0.0.1` 的中文表头；不再生成 `pending_confirmations.csv`，待确认信息保留在各决策记录和 `modeling_state.json` 中。审计覆盖率必须为 100%，审计文件缺失或表头不匹配时任务失败。

VIEW JOIN 只证明查询关联，不证明派生血缘；使用 `VIEW_JOIN_EVIDENCE`、`VIEW_DERIVATION_LINEAGE`、`VIEW_CALCULATION_LOGIC`、`VIEW_FILTER_LOGIC` 区分语义。显式 FK 通常只能确认 REFERENCE，不能单独确认 COMPOSITION 或 TRANSFORMATION；声明 FK 与运行时 enforced 必须分开记录。关系用稳定的 `relation_decision_id` 唯一标识，同一端点可存在多种关系。

规则必须分离 Discovery/Existence、Validation、Enforcement、Effectiveness；0 violation 只能是 OBSERVED_ONLY，不能证明规则存在或已强制执行。规则决策（CONFIRMED/CANDIDATE/REJECTED）与强制状态独立：CONFIRMED 规则允许强制状态=UNKNOWN/NOT_ENFORCED，并可正常正式输出；只有连存在证据都没有时才降为 CANDIDATE。ALERT 的 hit 不等于 violation，也不等于 effectiveness；没有 action 证据时 action 保持 UNKNOWN。物理字段不是业务指标，指标必须保留 grain、scope、unit、formula_status 和 aggregation_semantics；没有聚合证据时比例不得自动 AVG。

任何 UNKNOWN/UNRESOLVED → CONFIRMED 都必须记录新的独立 evidence IDs；没有新证据的状态升级必须报错。正式输出只消费已通过门禁的 Decision Layer，Generator 不得自行修改语义状态。
