# 版本管理规范

## 目标

为 ontology-agent 建立长期、稳定、可执行的语义化版本管理规则，明确 Git commit、每日 changelog、正式版本文档、Git tag、GitHub Release 和服务器部署各自的职责，避免把日常提交、部署动作与正式版本号机械绑定。

## 版本号规则

版本格式：`vMAJOR.MINOR.PATCH`。

当前处于 `v0.x.y` 阶段：

- MAJOR：正式稳定后发生重大不兼容变化时升级；
- MINOR：出现一组用户可感知的新能力、重要兼容变化或阶段性功能集合时升级；
- PATCH：缺陷修复、性能优化、交互调整和小范围兼容改进时升级。

明确：

- `v0.x.0`：一组可感知的新能力；
- `v0.x.y`：修复、优化和小调整。

## 什么时候升级版本

- 每天 `v0.1.1 → v0.1.2` 在“每天给业务方一个明确、可回滚发布编号”的场景下是合理的；
- 但不是每天有 commit 就必须升级版本；
- 每周直接升级 `v0.2.0` 通常偏快；
- 是否升级 MINOR 由功能变化决定，不由自然周决定；版本升级不按自然周机械升级；
- 如果一周只有修复，继续增加 PATCH；
- 如果一天只有文档、测试或内部维护，可以不发布正式版本；
- 不允许为了满足日期节奏创建没有实际发布意义的版本号。

## 提交、部署与正式版本的边界

- 每次部署都要记录 commit 和每日 changelog；
- 但每次部署不一定创建新正式版本；
- 临时修复、验证部署、同版本重新部署可以继续使用当前正式版本，并记录部署 commit；
- 只有需要形成稳定、可回滚、可对业务方声明的版本快照时，才创建新版本号和 tag；
- 同一个正式版本不得对应多个内容不同的 tag；
- 已创建的 tag 不得移动。

### 每日稳定发布

- 如果每天都向业务方交付一个稳定、可回滚版本，可以每天增加 PATCH；
- 示例：
  - `v0.1.1`：修复加载卡顿；
  - `v0.1.2`：修复会话终态；
  - 只有文档修改：不创建正式版本；
  - 新增完整决策行动模块：升级 `v0.2.0`；
  - 修复 `v0.2.0`：发布 `v0.2.1`。

## 版本发布流程

一个正式版本至少满足：

1. 确定版本号；
2. 相关测试通过；
3. `git diff --check` 通过；
4. 更新 `docs/versions/vX.Y.Z.md`；
5. 更新 `docs/versions/README.md`；
6. 更新每日 changelog；
7. 创建一个冻结元数据 commit；
8. 双推分支；
9. 创建 annotated Git tag；
10. 将同一个 tag 推送到 origin 和 personal；
11. 验证两个远端 peeled commit 一致。

GitHub Release：

- 不是每个 tag 都必须立即创建；
- 只有用户明确要求创建 Release 时才执行；
- Release 必须绑定已有 tag，不得创建不同历史。

服务器部署：

- 只有用户在当前任务明确要求部署目标版本时执行；
- 部署必须校验目标 tag/commit；
- 不得仅因为分支更新而自动部署。

## 文档职责

| 载体 | 职责 |
| --- | --- |
| Git commit | 每次工程修改的最小历史单元 |
| 每日 changelog | 当天最终工程变化、验证和部署事实 |
| docs/versions/vX.Y.Z.md | 正式版本的用户可见能力、兼容性、限制和升级说明 |
| Git tag | 正式版本不可移动的 Git 快照 |
| GitHub Release | 可选的对外发布页和附件载体，需要用户明确要求 |
| 服务器部署 | 将指定 commit/tag 应用到服务，需要用户当前明确授权 |

必须明确：

- commit ≠ tag
- push ≠ 部署
- tag ≠ 部署
- GitHub Release ≠ 部署
- 部署 ≠ 必然创建新版本

## 后续版本规则

- `v0.1.0` 定版后不再修改其 tag；
- 后续普通修改先进入开发分支；
- 修复和小调整计划进入 `v0.1.1`；
- 一组明显新功能才进入 `v0.2.0`；
- 版本文件在正式定版前可以标记“开发中”；
- 正式定版后状态改为“已定版”；
- 已定版版本文档只能修正明显文档错误，不得把后续功能补写成旧版本能力。

## 禁止事项

- 禁止 `git tag -f` 覆盖或移动已定版 tag；
- 禁止 force push 改写已推送历史；
- 禁止 `git push --tags` 无差别推送 tag；
- 禁止为了满足日历节奏机械升级版本；
- 禁止把每次部署都升级为正式版本；
- 禁止把 GitHub Release 或部署动作视为日常 push 的组成部分；
- 禁止在未获用户当前明确授权时创建 Release 或执行部署。
